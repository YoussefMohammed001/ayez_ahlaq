- Conclusion: our app sends the correct payload and just displays whatever the server echoes back. ### Items 11, 37 — notifications don't show outside the app (no banner, no badge) — ✅ **FIXED**
FCM/local-notification infrastructure is mostly implemented (`lib/core/notifications/notification_service.dart`, uses `firebase_messaging` + `flutter_local_notifications`, wired via `lib/core/di/services_locator.dart:705-712`) — this is not a pull-only/REST-only model. Four concrete issues found:
1. **Root cause — foreground display logic is inverted.** `notification_service.dart:216-222`:
   ```dart
   FirebaseMessaging.onMessage.listen((RemoteMessage message) {
     if (message.notification == null) {
       _showNotification(message);
     }
     _refreshUnseenNotifications();
   });
   ```
   `_showNotification` only fires for **data-only** payloads. If backend sends a standard FCM message with a `notification` block (typical), foreground/backgrounded-but-alive app shows nothing — only the in-app list gets refreshed via `_refreshUnseenNotifications()`. This is why it "arrives" (visible once you reopen/go into the app) but never shows as a system banner.
2. **Missing Android permission.** `android/app/src/main/AndroidManifest.xml` has no `<uses-permission android:name="android.permission.POST_NOTIFICATIONS"/>`. On Android 13+, without this, no notification can display regardless of code correctness.
3. **Missing AOT annotation.** `backgroundHandler` (`notification_service.dart:28`) is registered via `FirebaseMessaging.onBackgroundMessage` but lacks `@pragma('vm:entry-point')`, required on Android release/AOT builds for the handler to be found as a standalone isolate entry point.
4. **Badge count — not implemented at all.** No `flutter_app_badger`/`app_badge_plus`/manual badge package anywhere in `pubspec.yaml` or `lib/`. Only `badge: true` flags are set (which just permit iOS to show a badge *if* the server sends `aps.badge` — no evidence that field is being sent). This is a genuine gap on both platforms.

Fix: (a) change the foreground listener to always call `_showNotification` regardless of `message.notification`, (b) add `POST_NOTIFICATIONS` to AndroidManifest.xml, (c) add `@pragma('vm:entry-point')` to `backgroundHandler`, (d) implement an app badge package + call it alongside `_refreshUnseenNotifications()` (and confirm backend sends `aps.badge` for iOS).

**Fix applied:**
1. `notification_service.dart:216-221` — removed the `if (message.notification == null)` guard; `_showNotification(message)` now always runs in `FirebaseMessaging.onMessage.listen`.
2. `android/app/src/main/AndroidManifest.xml` — added `<uses-permission android:name="android.permission.POST_NOTIFICATIONS"/>`.
3. `notification_service.dart:28` — added `@pragma('vm:entry-point')` above `backgroundHandler`.
4. Added `app_badge_plus: ^1.2.4` to `pubspec.yaml` (actively maintained, supports iOS/Android/macOS via a single `AppBadgePlus.updateBadge(count)` call, no extra native setup needed beyond the notification permission already requested in `_requestPermissions()`). `_refreshUnseenNotifications()` is now `async`, awaits each user-type cubit's `refreshUnseenCount()`, reads the resulting `state.unseenCount`, and calls a new `_updateBadge(count)` helper that no-ops when `AppBadgePlus.isSupported()` is false. Confirming the backend sends `aps.badge` for iOS is still worth a follow-up check but is not required for the Android/local-count path to work.
- `flutter analyze` on `notification_service.dart` shows only 3 pre-existing issues untouched by this change (`_context`/`_pollingTimer` unused fields, one unrelated `use_build_context_synchronously` at line 297 inside `handleNotificationTap`).

### Item 25 — "booking requested" / barber order notifications show in English inside Arabic UI — **BACKEND (not a Flutter string bug)**
- Confirmed: `"booking requested"` is **not** a hardcoded Dart string anywhere (`grep -rniE "booking[ _]?requested"` across `lib/**/*.dart` and `.arb` files → zero matches). The only near-hit is the enum `NotificationKind.bookingRequested` used purely for icon selection, not display text.
- The proper booking-status UI (chips like "قيد الانتظار", "مؤكد" etc.) IS correctly localized via a mapping layer — `booking_status_label.dart` / `customer_booking_status_label.dart` switch over a `BookingStatus` enum to `S().bookingStatusXxx`. This mechanism works. There's no `requested` case in that enum though (closest is `pending`), and no `bookingStatusRequested` key exists in either `intl_en.arb` or `intl_ar.arb`.
- **Root cause:** the notification text itself — both the push banner and the in-app notification list — renders `message.notification?.title` / `.body` (or `notification.title`/`.body` from the REST list) **verbatim from the backend**, with zero `S()`/l10n involvement (`lib/core/notifications/notification_service.dart:180-211`, `notification_row.dart:57,76`, `customer_notification_row.dart:55,71`).
- Conclusion: this text is composed server-side inside the FCM payload. **Not fixable purely on our side.** Needs backend to either (a) send localized text per the user's language, or (b) switch to data-only messages with a status/type code that we map client-side (same pattern as `booking_status_label.dart`).

### Item 28 — merchant "add category" error on Free plan shows in English — **BACKEND (app-wide pattern, not this flow specifically)**
- Chain: `add_category_sheet.dart` → `merchant_categories_cubit.dart` → `CreateCategoryUseCase` → `merchant_categories_repo.dart` → API → `NetworkService._safeRequest` (`lib/core/network/dio/network_service.dart:18-61`).
